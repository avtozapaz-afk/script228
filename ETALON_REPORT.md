# Эталон 200 заявок — что удалось померить

Файл: `data/reference/AVTOZAP_etalon_200.xlsx` → вход `data/etalon_200.jsonl`.
Точка отсчёта из разметки подтверждена расчётом: **боевая система права в
128 из 200 (64.0%)**.

## Главное: цифры рядом со 128 у меня нет

Прогнать цепочку по 200 заявкам я не смог — в моём окружении нет
`OPENAI_API_KEY`. Всё, что требует живого арбитра, осталось невыполненным, и
выдавать вместо этого mock-число было бы враньём: заглушка арбитра намеренно
осторожна и на этих же 200 заявках даёт 84/200, что характеризует заглушку, а
не цепочку.

Команда, которая даёт недостающее число:

```bash
python run_test.py --input data/etalon_200.jsonl
python scripts/score_etalon.py --results out/results.jsonl
```

Второй командой печатается и сама цифра, и разбивка по уверенности арбитра —
та самая таблица, по которой выбирается порог.

## Что померить удалось: потолок цепочки

Он считается без API и говорит, на что цепочка вообще способна: арбитр
выбирает только из того, что дал ретривер, — выше этого потолка подняться
нельзя физически.

| | заявок | доля |
|---|---|---|
| заявок с ожидаемым кодом | 173 | |
| правильный код в shortlist, поиск по сырому тексту | 151 | 87.3% |
| **правильный код в shortlist после Layer 0** | **154** | **89.0%** |
| из них он на первом месте | 98 | 56.6% |

С учётом 27 заявок, где правильный ответ — отказ (их цепочка закрывает
отказом, и это попадание):

**Потолок = 181 / 200 = 90.5%. Запас над боевыми 128 — плюс 53 заявки.**

Читать это надо так: 181 — это если арбитр не ошибётся ни разу. Реальный
результат будет ниже, и разница между ним и 181 — цена ошибок арбитра. Ровно
это и покажет прогон.

Вклад сегментации виден отдельно: +3 заявки (151 → 154). Немного, но в длинных
сообщениях на десяток деталей поиск по всему тексту нужную деталь физически не
находит, и без Layer 0 они были бы потеряны все.

Пока его нет, цепочка отвечает `UNRESOLVED` → отказ, и по вашему правилу это

### Порог уверенности

Правило заложено в `avtozap/policy.py` как отдельный слой — он ничего не
выбирает и не отменяет решений арбитра, только переводит их в действие:

| действие | когда |
|---|---|
| `ANSWER` | деталь определена, код уходит дальше |
| `ASK_BUYER` | не уверены — просим описать деталь другими словами |
| `ASK_PHOTO` | покупатель сам пишет, что не знает названия |
| `PASS_TO_SHOP` | второй заход не помог — сырой текст уходит магазинам |
| `ERROR` | сбой конвейера, а не вопрос покупателю |

Второй заход задаётся флагом `--attempt 2`: на нём цепочка больше не
переспрашивает, а отдаёт заявку магазинам.

`ASK_PHOTO` срабатывает по фразам из живых заявок, не по выдуманным:
`adını bilmirəm`, `başqa adı bilmirem`, `не знаю как называется`,
`şəkil göndərdim`. Проверено, что обычная заявка под них не попадает. Просьба
о фото имеет приоритет над «отдать магазинам»: если покупатель не знает
названия, фотография полезнее сырого текста.

Действие и вопрос покупателю пишутся в CSV колонками `action`,
`action_reason`, `buyer_question`.

**Сам порог я назначить не могу — его считает прогон.** `score_etalon.py`
печатает долю попаданий по каждому уровню уверенности арбитра (`high`,
`medium`, `low`), и порог ставится там, где доля падает. Сейчас в конфигурации
принимаются `high` и `medium`, `low` уходит в переспрос — это разумная
отправная точка, но её надо подтвердить или подвинуть по таблице.

### Дубли кодов — поправка принята

Вы правы, вешать `abornu` на RG-04 нельзя. Все три дубля заведены в
`data/duplicate_codes.json` и сводятся автоматически:

| дубль | канонический | деталь |
|---|---|---|
| RG-04 | MU-089 | воздушный патрубок |
| MU-012 | MU-078 | прокладка ГБЦ |
| SO-025 | SO-005 | корпус термостата |

Сведение работает в трёх местах: дубль не попадает в shortlist (предлагать
арбитру исчезающий код нельзя), наружу отдаётся только канонический код, и
сверка с эталоном тоже канонизирует обе стороны. Проверено тестом, что ни один
ожидаемый код в разметке не является дублем — разметка чистая.

Побочный эффект: сверка с devset fresh-300 перестала совпадать ровно на этих
трёх кодах, и это правильно. Тест обновлён, чтобы сверять канонические коды.
