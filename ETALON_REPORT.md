# Эталоны — что удалось померить

В проекте теперь два размеченных набора, и они меряют **разное**. Оба нужны.

| набор | заявок | что меряет |
|---|---|---|
| `data/etalon_469.jsonl` ← `AVTOZAP_ETALON_GOTOVYY.csv` | 469 | **точность**: у каждой заявки есть правильный код |
| `data/etalon_200.jsonl` ← `AVTOZAP_etalon_200.xlsx` | 200 | **поведение**: 27 заявок, где верный ответ — отказ или переспрос, плюс точка отсчёта 128 |

Пересобрать оба: `python scripts/build_etalon_input.py`.

## Почему старый набор нельзя выбрасывать

Новый файл пересекается со старым всего по **27 текстам из 469**, то есть это
не исправленная версия, а другая выборка. И главное:

* в новом наборе **нет ни одной заявки с пустым правильным кодом** — из тех 27
  «отказных» строк старого набора в новый не попала ни одна;
* в новом наборе **нет колонки с ответом боевой системы**, то есть точки
  отсчёта «128 из 200» в нём тоже нет.

Правило «не уверен — переспроси, не знаешь названия — проси фото» осталось без
изменений, как вы и сказали. Но проверить его можно только на наборе из 200:
если считать лишь по 469, система, которая никогда не отказывается, выглядит
безупречной по этой оси. Поэтому оба набора остались, и оба покрыты тестами.

Единственное расхождение по общим текстам — одно, и оно осмысленное:
`on podpresin surucu teref kanti` был KZ-038 (общий «хром-кант»), стал KZ-095
(«кант лобового стекла»). Разметка стала точнее.

## Словарь 571 — все 469 строк считаются

Выгрузка от 01.09 закрыла вопрос: KZ-094 и KZ-095 на месте, строк вне подсчёта
больше нет. Механизм `scorable` остался — если разметка снова обгонит словарь,
такие строки не будут ни засчитаны, ни провалены.

Контрольный прогон проекта воспроизводится **точно: 485 / 70 / 149**. Это и
есть доказательство, что репозиторий запускает движок проекта как есть; теперь
оно закреплено тестом вместо устаревшей сверки со ссылочными shortlist
fresh-300 (те считались словарём 541 и прежним движком).

## Потолок цепочки

Считается без API. Арбитр выбирает только из того, что дал ретривер, — выше
этого подняться нельзя физически.

| | набор 469 | набор 200 |
|---|---|---|
| заявок с ожидаемым кодом | 469 | 173 |
| код в shortlist по сырому тексту | 463 = 98.7% | 157 = 90.8% |
| **код в shortlist после Layer 0** | **465 = 99.1%** | **160 = 92.5%** |
| из них на первом месте | 334 = 71.2% | 114 = 65.9% |
| потолок всей цепочки | **465/469 = 99.1%** | **187/200 = 93.5%** |

Было до словаря 571: 90.3% и 90.5%, промахов 45 и 19. Стало 99.1% и 93.5%,
промахов 4 и 13. На наборе 200 запас над боевыми 128 — **плюс 59 заявок**.

Разница между потолком и результатом прогона — цена ошибок арбитра. Ровно её и
покажет живой прогон.

## Цифры прогона по-прежнему нет

`OPENAI_API_KEY` в моём окружении нет, прогнать цепочку по API я не могу.
Mock-число подставлять не буду: заглушка арбитра осторожна по построению и
описывает саму себя, а не цепочку.

```bash
python run_test.py --input data/etalon_469.jsonl
python scripts/score_etalon.py --results out/results.jsonl

# и отдельно — проверка правила отказов и переспроса
python run_test.py --input data/etalon_200.jsonl
python scripts/score_etalon.py --etalon data/etalon_200.jsonl --results out/results.jsonl
```

Второй командой печатается доля попаданий по каждому уровню уверенности
арбитра — по ней и ставится порог.

## Правило переспроса и фото — без изменений

Как договорились, `avtozap/policy.py` не трогал:

| действие | когда |
|---|---|
| `ANSWER` | деталь определена |
| `ASK_BUYER` | не уверены — просим описать другими словами |
| `ASK_PHOTO` | покупатель сам пишет, что не знает названия |
| `PASS_TO_SHOP` | второй заход (`--attempt 2`) не помог — сырой текст магазинам |

Просьба о фото по-прежнему имеет приоритет над «отдать магазинам».

## Два согласованных правила — сделаны

**Вязкость вместо марки** (`avtozap/lubricants.py`). `5w-40`, `0/20`, `75W90`,
`DOT-4` — это формат, а не словарь, и по нему видно, что речь о масле или
тормозной жидкости, какая бы марка ни стояла рядом. Обе заявки на масло из
списка промахов закрылись. Трансмиссионное отличается от моторного: рядом со
словом `karopka` вязкость читается как трансмиссионная. Размер шины
`205/55R16` под правило не попадает — проверено.

**Ранжирование по головному слову** (`avtozap/head_ranking.py`). Отдельный
проход поверх вендорного ретривера, его код не тронут — контрольные 485/70/149
остаются теми же по построению. Головой считаем последнее слово, **известное
словарю**: в `Qabaq sağ sol çaşka lenforderle` хвостовая марка головой не
становится.

Замер: на наборе 469 доля «код на первом месте» выросла с 323 до 334 заявок
(+11). На наборе 200, который в подборе не участвовал, — без изменений, 114.
Состав shortlist не меняется ни на одном наборе, потолок правило не двигает.

Прирост скромнее, чем ожидалось: словарь 571 уже закрыл большинство
конструкций «владелец/деталь» выверенными контекстными правилами, и общему
правилу досталась остаточная часть.

Штраф кандидату без головного слова я пробовал и **убрал**: с ним rank#1 падал
до 319, то есть хуже, чем совсем без правила. Большая надбавка тоже вредит —
0.02 даёт +6, 0.06 уже −4. Оставлено 0.01.

## Что осталось в ретривере — 4 заявки из 469

Было 45, стало 4. Все четыре — одна и та же конструкция «владелец/деталь»,
которую не закрыли ни ваши контекстные правила, ни моё общее:

| заявка | нужен | ретривер дал |
|---|---|---|
| `arxa baqaj qapisina rucka lazımdır` | KZ-016 Ручка двери | KZ-033 Крышка багажника |
| `Radiator bacokun qapaqi` | SO-032 Крышка бачка | SO-008, SO-001 Радиатор |
| `Giriş kollektorun prokladkası (boğaz rezini)` | MU-087 Прокладка коллектора | MU-082, MU-083 |
| `Qabaq sağ sol çaşka lenforderle` | AS-029 Нижняя чашка пружины | TR-007, AS-034, AS-011 |

Почему моё правило их не взяло:

* `rucka`, `qapaqi` — головное слово есть, но имя нужной детали в словаре
  записано иначе (`Qapı qulpu`, `Bacokun qapağı`), и совпадения по имени не
  происходит. Надбавка вешается на имя намеренно: по синонимам крышка бачка
  неотличима от самого бачка.
* `çaşka` — деталь AS-029 в shortlist вообще не попадает, поднимать нечего.
  Тут нужен синоним, а не ранжирование.

Это четыре точечных случая, и я бы их закрыл контекстными правилами того же
вида, что вы уже завели (`radiator + bacok + qapaq` → SO-032). Скажу прямо:
общее правило свою часть выбрало, дальше дешевле точечные.
