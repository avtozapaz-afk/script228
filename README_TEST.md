# AVTOZAP — сквозной тестовый прогон конвейера

Харнесс прогоняет **сырой текст покупателя** через весь конвейер и выдаёт по
каждому запрошенному предмету итоговый `part_id` либо честный `UNKNOWN`.

```
RAW REQUEST
  → Layer 0 (сегментатор)
  → OEM / part-number резолвер
  → слой фото-доказательств
  → Retriever V2
  → Arbiter V3 (ЗАМОРОЖЕН)
  → Валидатор
  → итоговый part_id / UNKNOWN
```

Только Python 3.9+ (проверено на 3.11). Ни `.cmd`, ни `.bat`, ни PowerShell
не требуется; в режимах `--mock` и `--dry-run` не нужен даже пакет `openai`.

---

## Запуск за три шага

```bash
pip install -r requirements.txt          # 1. один раз
export OPENAI_API_KEY="sk-..."           # 2. или пропустите — спросит скрытым вводом
python run_test.py --input data/requests_300.jsonl    # 3.
```

На выходе в `out/` (папка создаётся сама):

| файл | что внутри |
|---|---|
| `results.jsonl` | по строке на атомарный предмет, пишется сразу — основа возобновления |
| `results.csv` | та же таблица в плоском виде для Excel (UTF-8 BOM) |
| `summary.json` | сводка в машинном виде |
| `summary.md` | сводка для чтения: статусы, слои, список провалов по слабому звену |
| `errors.log` | трассировки сбойных запросов |

Прогон **возобновляемый**: результат каждого предмета сбрасывается на диск
немедленно, повторный запуск той же команды пропускает уже посчитанное.
Прервать можно в любой момент, включая `Ctrl+C`, — ничего не теряется.

### Ключ API

Сначала читается переменная `OPENAI_API_KEY`. Если её нет, ключ спрашивается
скрытым вводом. Ключ **никогда** не печатается, не пишется в результаты и не
попадает в логи; тест `test_the_api_key_never_reaches_the_output` это проверяет.

## Формат входа

JSONL (по объекту на строку) или CSV. Обязательное поле одно — текст запроса.

```json
{"rfq_id": "req-001", "original_text": "Naklatka və tormuz disk", "expected_part_id": "EY-001"}
{"rfq_id": "req-002", "original_text": "ön bufer", "image_path": "photos/req-002.jpg"}
```

| поле | обязательное | назначение |
|---|---|---|
| `original_text` (или `text`) | да | сырое сообщение покупателя |
| `rfq_id` | нет | идентификатор; иначе подставляется `row-N` |
| `expected_part_id` / `expected_part_ids` | нет | эталон: включает точность и разбор по слоям |
| `image_path` / `image_url` | нет | фото для слоя фото-доказательств |

Эталон может быть списком (`["EY-001","EY-002"]`) или строкой через запятую.
Значение `UNKNOWN` означает, что правильный ответ — честный отказ.

Оценка идёт **по запросам**, а не по предметам: у сообщения может быть
несколько предметов, и требовать от каждого совпадения с одним `part_id`
было бы неверно.

## Флаги

| флаг | зачем |
|---|---|
| `--input ПУТЬ` | входной файл (по умолчанию `data/requests_300.jsonl`) |
| `--limit N` | только первые N запросов — дымовой тест на реальном API |
| `--mock` | без сети: детерминированная заглушка вместо Arbiter V3 |
| `--dry-run` | проверить вход, словарь, сегментацию и ретривер; API не трогать |
| `--no-resume` | начать заново, перезаписав `results.jsonl` |
| `--report-only` | пересобрать CSV и сводку из готового `results.jsonl` |
| `--model ИМЯ` | модель арбитра (по умолчанию `gpt-4o`) |
| `--top-k N` | кандидатов от Retriever V2 (по умолчанию 12) |
| `--min-score X` | порог отсечения кандидатов (по умолчанию 0.45) |
| `--min-confidence X` | ниже этой уверенности `SELECT` понижается до `REVIEW` (0.45) |
| `--timeout СЕК` / `--max-retries N` | таймаут и число попыток на вызов API (60 с, 5) |
| `--enable-photo` | включить слой фото (нужны `image_path`/`image_url`) |
| `--oem-catalog ПУТЬ` | JSON-каталог OEM-номеров (по умолчанию `data/oem_catalog.json`) |

Рекомендуемый порядок перед полным прогоном:

```bash
python run_test.py --input data/requests_300.jsonl --dry-run   # вход и словарь
python run_test.py --input data/requests_300.jsonl --limit 5   # 5 кейсов на API
python run_test.py --input data/requests_300.jsonl             # все 300
```

## Что делает каждый слой

### Layer 0 — сегментатор

Режет сообщение на **атомарные предметы: один предмет = один тип детали**.

| вход | результат |
|---|---|
| `Naklatka və tormuz disk` | 2 предмета: колодка + диск |
| `babin və sveça` | 2 предмета: катушка + свеча |
| `mühərrik və sürətlər qutusunun yastıqları` | 2 предмета: опора двигателя + опора КПП |

Не дробит, когда одну и ту же деталь просят в нескольких положениях:

| вход | результат |
|---|---|
| `ön və arxa bufer` | 1 предмет, `position = ön,arxa` |
| `sol və sağ güzgü` | 1 предмет, `side = sol,sağ` |
| `ön bufer və arxa bufer` | 1 предмет (одна и та же «голова») |

Отдельно вырезается контекст автомобиля (марка, модель, год) — он сохраняется в
`vehicle_context` и не участвует в поиске детали. Слово, которое есть в словаре
запчастей, из текста не вырезается никогда, чем бы оно ни выглядело.

Эллипсис (`mühərrik və … yastıqları` → `mühərrik yastıqları`) восстанавливается
**только если полученная фраза реально есть в словаре** — придумать деталь этим
механизмом невозможно.

Исходное сообщение целиком сохраняется как контекст, но матчинг ниже по
конвейеру работает по атомарному `item_raw`.

### OEM / part-number резолвер

Работает **до** Retriever V2. Отличает номер детали от VIN, года, кода кузова,
объёма двигателя, типоразмера шины, телефона и количества; собирает номера,
записанные группами (`1K0 615 301 AA`, `34 11 6 794 300`).

| статус | смысл |
|---|---|
| `MATCH` | номер и текст указывают на один объект |
| `CONFLICT` | номер указывает на **другой** объект, чем текст |
| `UNRESOLVED` | похоже на номер, но сопоставить не с чем |
| `NONE` | полезного номера нет |

**Номер никогда молча не перебивает текст.** При расхождении статус `CONFLICT`
доезжает до валидатора и уходит на разбор.

> ⚠️ Каталог OEM (`data/oem_catalog.json`) **в проект не передавался**. Пока его
> нет, любой найденный номер честно получает `UNRESOLVED` — выдумывать
> соответствие номера детали запрещено. Формат, когда каталог появится:
> `{"1K0615301AA": {"part_id": "EY-002"}}`. Ветки `MATCH` и `CONFLICT` написаны
> и покрыты тестами, они включатся сами, как только файл появится.

### Слой фото-доказательств

Если у запроса есть `image_path`/`image_url` и слой включён (`--enable-photo`),
изображение описывается vision-моделью. Результат — **текстовое описание и
слова-подсказки, никогда `part_id`**: фото помогает выбрать между реальными
кандидатами, но не разрешает выдумать деталь, которой нет в словаре. Отсутствие
или недоступность картинки фиксируется статусом (`NO_IMAGE`,
`IMAGE_UNAVAILABLE`) — конвейер спокойно едет дальше.

### Retriever V2

Отдаёт **только реальные записи словаря**. Каждый кандидат несёт `score` и
`reason`, по которым видно, почему он попал в список:

| reason | база | как найдено |
|---|---|---|
| `exact_name` | 1.00 | фраза равна варианту имени детали |
| `exact_synonym` | 0.95 | фраза равна синониму листа → все детали листа |
| `exact_leaf` | 0.90 | фраза равна имени листа словаря |
| `*_containment` | 0.62–0.95 | все токены записи покрыты запросом (или наоборот) |
| `fuzzy_*` | = сходство | опечатка в фразе целиком |
| `token_overlap` | 0.25–0.85 | частичное покрытие значимых токенов |

Полнота здесь важнее краткости: пропущенного ретривером кандидата арбитр уже не
спасёт. Чтобы полнота реально держалась, добавлены три вещи:

* **транслитерация кириллицы** — `тормозной` → `tormoznoy`, поэтому латинский
  ввод `tormuz disk` достаёт русский синоним «тормозной диск»;
* **согласный скелет** — `tormuz` ≡ `tormoz`, `apornu` ≡ `opornu` (словарь сам
  перечисляет оба варианта: гласные в транслите неустойчивы);
* **индексация имён листьев** — покупатель пишет `əyləc altlığı`, а это имя
  листа `Əyləc altlıqları (nakladkalar)`. Без этого целый класс запросов
  пролетал мимо правильной группы.

Вес последнего («головного») токена вдвое выше: и азербайджанский, и русский
head-final — тип детали несёт последнее слово.

Проверить, каких деталей не хватило в кандидатах, можно по колонке
`retriever_candidate_ids` в CSV и по счётчику
`retriever_misses_vs_expected` в сводке.

### Arbiter V3 — ЗАМОРОЖЕН

Промпт лежит в `avtozap/prompts/arbiter_v3.txt` и защищён контрольной суммой в
`arbiter_v3.sha256`. Тест `test_prompt_is_frozen` падает при любом расхождении,
поэтому незаметно «доработать по ходу дела» промпт невозможно.

На вход арбитру подаются `original_text`, атомарный `item_raw`, перевод (если
используется), контекст автомобиля, статус и номера OEM, статус фото и список
кандидатов Retriever V2. **Список кандидатов — единственный источник допустимых
кодов.** Если модель вернула код, которого там не было, это фиксируется как
ошибка формата и уходит в отчёт; «починить» ответ подстановкой нельзя.

Температура 0, ответ в JSON-режиме — прогон детерминирован настолько, насколько
это позволяет модель.

### Валидатор

Жёсткие проверки после арбитра. У каждой свой код, поэтому в отчёте видно не
только «отклонено», но и чем именно.

| код | действие | правило |
|---|---|---|
| `V1` | REJECT | выбранного `part_id` нет в словаре |
| `V2` | REJECT | код отсутствует среди разрешённых кандидатов |
| `V3` | DOWNGRADE | запрошенного объекта нет — выбран родитель/сосед |
| `V4` | DOWNGRADE | конфликт OEM не разрешён безопасно |
| `V5` | REJECT | Layer 0 оставил в предмете несколько разных типов деталей |
| `V6` | REJECT | состояние конвейера внутренне противоречиво |
| `V7` | DOWNGRADE | уверенность ниже порога (`--min-confidence`) |

`REJECT` переводит итог в `UNKNOWN`, `DOWNGRADE` — в `REVIEW`. Точность важнее
навязанной полноты: когда система не может безопасно опознать деталь, она
отвечает `UNKNOWN`/`REVIEW`, а не придумывает совпадение.

## Как читать результаты

Итоговый статус предмета — один из `SELECT`, `UNKNOWN`, `REVIEW`, `ERROR`.

Раздел «Провалы по слабому звену» в `summary.md` группирует неудачи по слою,
который **первым** потерял правильный ответ:

* `Layer 0 — сегментация` — предмет выделен неверно;
* `Retriever V2` — правильной детали **не было** среди кандидатов;
* `OEM-резолвер` — номер обработан неверно;
* `Arbiter V3` — правильный кандидат **был на руках**, но не выбран;
* `Валидатор` — арбитр был прав, а его зарубила проверка;
* `Ошибка конвейера` — исключение или сбой API.

Правило разбора: **Arbiter V3 обвиняется только тогда, когда правильный
кандидат был у него на руках**. Если правильной детали не было в кандидатах —
чинить надо ретривер, индексацию или словарь, а не арбитра. Если предмет выделен
неверно — Layer 0.

## Чего в проекте нет

Вместе с заданием эти файлы **не передавались**, и выдумывать их содержимое
нельзя:

1. **Свежие 300 запросов.** Положите их в `data/requests_300.jsonl` в формате
   выше. В `data/sample_requests.jsonl` лежат 12 **синтетических** строк — это
   дымовой набор для проверки механики, а не оценочная выборка.
2. **Каталог OEM-номеров.** До его появления номера получают `UNRESOLVED`.
3. **Фотографии запросов.** Без них слой фото возвращает `NO_IMAGE`.
4. **Исходный промпт Arbiter V3.** В репозитории его не было, поэтому промпт
   написан здесь по правилам из задания и заморожен контрольной суммой. Если у
   вас есть настоящий V3 — положите его в `avtozap/prompts/arbiter_v3.txt` и
   обновите сумму:
   ```bash
   python -c "import hashlib,pathlib; p=pathlib.Path('avtozap/prompts/arbiter_v3.txt'); \
   pathlib.Path('avtozap/prompts/arbiter_v3.sha256').write_text(hashlib.sha256(p.read_bytes()).hexdigest()+'\n')"
   ```

Реальный дымовой прогон по API в этом окружении **не выполнялся**: ключа
`OPENAI_API_KEY` здесь нет. Чтобы путь к API не остался непроверенным, он
покрыт тестами на подставном транспорте (`test_llm.py` и два теста в
`test_pipeline.py` гоняют настоящий `ArbiterV3` и настоящий `LlmClient`).
Первым делом на своей машине запустите `--limit 5`.
