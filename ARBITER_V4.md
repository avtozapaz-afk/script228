# Arbiter V4 — что изменено и как это проверить

Стратегия сменилась: цель — выйти в пилот, а не выжать эталон до 100%. Поэтому
здесь только то, что двигает семантику, и ни одного правила под конкретную
строку эталона.

## Сначала — технический дефект, не семантика

Живой прогон 200 дал 173/200. Разбор винил арбитра в 21 случае, но три заявки
были **дефектом OEM**, а не спором о смысле:

```
976742S000        каталог знает → SO-044   конвейер отдавал UNKNOWN
58323 2H300       каталог знает → EY-023   конвейер отдавал UNKNOWN
61664849598       каталог знает → EL-071   конвейер отдавал UNKNOWN
30939070 …        каталог знает → SR-005   конвейер отдавал UNKNOWN
```

Резолвер честно возвращал `MATCH` с верным кодом — а итог собирался только из
решения арбитра, и номер терялся. Починено: разрешённый номер теперь отвечает
сам. Номер детали не догадка и не «похожая по теме» деталь; если покупатель
прислал артикул и он найден, спрашивать нечего.

Конфликт номера с выбором арбитра сюда **не** попадает: он остаётся у правила
V4 валидатора и по-прежнему уходит в разбор — номер может относиться к другой
детали из того же сообщения.

**+4 заявки без единой правки семантики.**

## Три класса ошибок, а не двадцать один случай

Оставшиеся ошибки прогона укладываются в три класса. Каждое правило V4 отвечает
классу.

**Класс А — верный кандидат стоял первым, модель ушла в сторону (8 заявок).**
`qabağ naklatka` → колодка была №1, выбрана накладка бампера. `torpedo şit` →
щиток приборов был №1, выбрано торпедо. `sol ön fara lupa ilə` → фара была №1,
выбрана линза — хотя в самом промпте V3 написано «fara lupa ilə = WHOLE
HEADLIGHT». Правило было, и модель его не применила.

**Класс Б — судит по всему сообщению вместо своего предмета (3–4 заявки).**
Предмет `Yağ filtri`, ответ — «в запросе две детали, уточните». Две детали были
в сообщении, а Layer 0 их уже разделил, и второй занимался отдельный запуск.

**Класс В — уверенный ответ там, где нужен отказ (2 заявки).** `G12 paket` —
это спецификация антифриза, а не деталь. `line keçə … başqa adı bilmirəm` —
покупатель прямо пишет, что названия не знает.

## Что в V4 сделано

| правило | против чего |
|---|---|
| **Судить только `item_raw`.** Остальные предметы сообщения разбираются своими запусками; `clarify` за многодетальность — только если две детали внутри самого предмета | класс Б |
| **Первый кандидат — ответ по умолчанию.** Уйти от него можно, лишь назвав слово из запроса, которое покрывает другой кандидат. Не уходить потому, что другая деталь «типичнее» | класс А |
| **Точный термин и OEM — факты, а не подсказки.** В payload лежат `retrieval_reason` вида `exact:` / `context:` и разрешённый номер; V3 про них не знал и называл ранг «лишь подсказкой» | пункт 6 задания |
| **Голова — последнее существительное**, предыдущие слова это владелец. Не добавлять существительное, которого покупатель не писал, и не подниматься к узлу, если названа деталь | класс А |
| **Отказ на «пакет / марка / не знаю названия»** и на фрагмент без существительного-детали | класс В |
| **`low` — не ответ.** Угадываешь — переспроси | пункт 5 задания |

Контракт ответа не менялся: те же `select/unknown/clarify`, тот же JSON.
Поэтому валидатор, политика и отчёты работают как были.

**V3 не тронут.** Его промпт по-прежнему заморожен и сверяется контрольной
суммой — иначе сравнивать было бы не с чем. V4 лежит рядом:
`--arbiter v3|v4`, по умолчанию v3. Версия и хеш промпта печатаются в каждый
отчёт: одинаковые цифры могут оказаться от разных правил.

## Как сравнить

```cmd
python SRAVNENIE_V3_V4.py
```

Четыре прогона (две версии × два эталона) и таблица. Возобновляемый: прервали —
запустите ту же команду. Только один набор: `--only 200`.

Таблица считает пять чисел, но решают два:

| | что значит |
|---|---|
| **правильные ANSWER** | заявка закрыта верно; многодетальная — только если найдены все коды |
| **ОПАСНЫЕ ложные ANSWER** | уверенно ответили там, где нужен был переспрос |
| ошиблись кодом | ответили, но не тем |
| переспросили зря | отказались там, где код был в shortlist |
| переспросили верно | отказались там, где отказ и требовался |

Три последних разделены не для красоты: осторожная версия набирает мало
опасных, но много «зря», и по одной сумме этого не видно.

**Точка отсчёта V3 на наборе 200** (посчитана по вашему прогону):

```
правильные ANSWER        173
ОПАСНЫЕ ложные ANSWER      2
ошиблись кодом            17
переспросили зря           8
переспросили верно         4
```

Скрипт печатает вердикт по вашему правилу: принимаем V4, если верных стало
больше, а опасных не больше. Если опасных прибавилось — решение за вами,
скрипт сам V4 не примет.

## Очередь пилота

Каждый прогон теперь пишет `pilot_queue.jsonl` — заявки, где система
**переспросила или ошиблась**. Заявка, закрытая верно и без вопросов, туда не
попадает.

У каждой записи есть пустое поле `correct_external_code` — его заполняет
человек. Заполненный файл и есть пополнение эталона: формат тот же, что у входа
прогона, так что его можно подать обратно без переделки.

Это работает и на живом потоке, где ожидаемого кода нет вовсе: туда попадёт всё,
на чём система запнулась. С первого дня пилота — как вы и просили.

## Чего V4 не чинит и чинить не должен

Три заявки набора 200 лежат за пределами задачи арбитра, и ими правильно
заниматься отдельными слоями, а не промптом:

* `25819 0W010` — номера нет в каталоге OEM;
* `Bu firmaynan var?` — ответ в предыдущем сообщении переписки;
* `amerikanka 3 lupa cut` — сленг, которого нет в словаре.

Словарь и ретривер заморожены, массовая чистка прекращена.
