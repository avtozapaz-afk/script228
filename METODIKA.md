# Методика: что именно означает каждая цифра

Документ для того, кто будет проверять цифры, а не верить им. Здесь только
определения и команды воспроизведения. Никаких выводов — они в
`ETALON_REPORT.md`.

Главное предупреждение сразу, потому что на этом легче всего ошибиться:

> **499 / 68 / 137, 467/469 и 411 — три разные вещи, измеренные на трёх разных
> наборах тремя разными способами. Между собой они не сравниваются.**

---

## 1. Тройка «499 / 68 / 137» — контрольный прогон матчера

**Что это.** Собственный критерий приёмки проекта, тот же, что в `prognat_704.py`.
Меряет **только словарь и движок матчера**. Ни Layer 0, ни LLM, ни арбитра тут
нет вообще.

**Зачем нужно.** Это не оценка качества. Это доказательство, что репозиторий
запускает движок проекта **как есть**, ничего не исказив. Если цифра совпала до
единицы — вендорный код не переписан.

**Откуда берётся выборка.** `data/reference/zayavki/zayavki_6188.json` — 6188
живых заявок, четыре поля: `[дата, текст, подтверждённое_название_детали, —]`.
Берутся строки, где третье поле непустое **и точно совпадает** (после
`strip().lower()`) с `name_ru` какой-нибудь детали словаря. Таких строк
**704**. Это и есть эталон матчера: покупатель подтвердил, что за деталь.

**Как считается.** Для каждой из 704 строк вызывается `match(text)` вендорного
`avtozap_matcher_engine`, возвращающий `(код, причина)`:

| исход | условие | v7 |
|---|---|---|
| **верно** | `код == ожидаемый` | 500 |
| **неверно** | код выдан, но другой | 68 |
| **не найдено** | `код is None` | 136 |

Сумма всегда 704.

**Воспроизвести:**

```bash
python3 -m pytest tests/test_retriever.py::test_the_project_control_run_reproduces_exactly -q
```

Тест ассертит ровно `(500, 68, 136)`. Числа по поставкам словаря:
541 деталь — 485/70/149; выгрузка 01.09 — 500/69/135; v7 — 499/68/137;
v8 — 500/68/136.

**Каждое изменение этой тройки сверяется построчно, а не принимается на веру.**
В v7 «верно» стало меньше на единицу — изменились ровно три строки из 704:
`Sağ tərəf almacıq` починился (SU-002 → SU-003), а два `Arxa şveller`
перестали матчиться, потому что термин `sveler` объявлен неоднозначным. Это
было сознательное решение проекта не угадывать между порогом и усилителем
бампера, а не регресс. В v8 изменилась ровно одна строка:
`aktivatur turbnun ustundə olan` стала находить MU-038.

## 2. «Потолок 467/469» — верхняя граница цепочки, НЕ точность

**Это самая частая ошибка чтения, поэтому явно:**

> **467/469 — это НЕ «система отвечает правильно в 99.6% случаев».**
> Это «в 99.6% случаев правильный код вообще присутствовал в списке, из
> которого арбитру предстояло выбирать». Сколько раз он выберет верно — цифра
> совсем другая, и её без ключа API не существует.

На эталоне 469 после словаря v8 потолок равен **469/469 = 100%**: правильный
код есть в shortlist у каждой заявки. Это не значит, что система отвечает
верно в 100% случаев — см. предупреждение выше.

**Смысл.** Арбитр не придумывает код, он выбирает из shortlist ретривера. Если
правильного кода в shortlist нет — арбитр не может ответить верно физически.
Значит доля «код попал в shortlist» — жёсткая верхняя граница для всей цепочки.
Разница между потолком и результатом живого прогона и есть цена ошибок арбитра.

**Алгоритм** (`scripts/score_etalon.py`, функция `retriever_ceiling`):

1. Берутся строки эталона, у которых есть ожидаемый код и стоит `scorable`
   (в v7 нескорируемых нет — все ожидаемые коды есть в словаре).
2. Сырой текст заявки прогоняется через **детерминированный** Layer 0
   (`avtozap/layer0.py`) → список атомарных предметов.
3. Для каждого предмета берётся shortlist ретривера, **лимит 24**
   (`RETRIEVER_LIMIT` в `avtozap/config.py`).
4. Заявка засчитана, если ожидаемый код есть **хотя бы в одном** из shortlist'ов
   её предметов.

**Три оговорки, которые надо знать при анализе:**

* Потолок меряется **детерминированным** Layer 0, а в живом прогоне работает
  LLM-сегментер (`avtozap/segmenter.py`), для которого детерминированный —
  запасной вариант. На длинных многодетальных заявках живой прогон может
  сегментировать иначе, поэтому потолок — оценка, а не гарантия.
* Печатаются **два** числа: «по сырому тексту» (поиск по всей заявке целиком) и
  «после сегментации». Разница между ними — вклад Layer 0.
* На наборе 200 в потолок дополнительно входят 27 заявок, где правильный ответ
  «кода быть не должно»: отказаться система умеет, значит эти заявки достижимы.
  Отсюда `164 + 27 = 191` из 200.

**Воспроизвести (API не нужен, ~1–2 минуты):**

```bash
python3 scripts/score_etalon.py                                # набор 469
python3 scripts/score_etalon.py --etalon data/etalon_200.jsonl # набор 200
```

## 3. «Код на первом месте 411» — качество ранжирования

Тот же цикл, что и потолок, но условие строже: ожидаемый код должен быть
**нулевым элементом** shortlist хотя бы одного предмета заявки
(`codes[0] == expected`).

**Зачем отдельная цифра.** Потолок с 01.09 не двигается вовсе — полнота
упёрлась. А rank#1 растёт: 334 → 406 → 411. Это прямой индикатор того, насколько
легко арбитру: чем чаще правильный код первый, тем меньше шансов, что модель
собьётся на похожего соседа. Чистки словаря видны именно здесь, а не в потолке.

**Сортировка shortlist** — `(-score, external_code)`. Обратите внимание: при
равных score порядок определяется **алфавитом кода**, то есть случайностью. Это
не декоративная деталь: именно так `MU-001` («Двигатель в сборе») обгонял
`SR-001` («Моторное масло») на запросе `Meguin 0/20`, пока не было починено.

## 4. Два эталона — они меряют РАЗНОЕ, и оба нужны

| | `data/etalon_469.jsonl` | `data/etalon_200.jsonl` |
|---|---|---|
| источник | `AVTOZAP_ETALON_GOTOVYY.csv` | `AVTOZAP_etalon_200_zayavok_FINAL.xlsx` |
| что меряет | **точность** | **поведение** |
| заявок | 469 | 200 |
| заявок «кода быть не должно» | 0 | **27** |
| ответ боевой системы записан | нет | **да, 128/200** |

**Почему нельзя выбросить набор 200.** Только в нём есть 27 заявок, где верный
ответ — отказ или переспрос, и только в нём есть точка отсчёта «боевая система
права в 128». Если считать лишь по 469, система, которая **никогда** не
отказывается, выглядит по этой оси безупречной.

**Правило подсчёта для этих 27** (задано заказчиком): выдала система код —
ошибка; переспросила, попросила фото или отказалась — попадание.

**Пересечение наборов — всего 27 текстов из 469.** Это разные выборки, а не
исправленная версия одной. Набор 200 собран из заведомо трудных случаев,
поэтому цифры на нём ниже, и сравнивать 469 с 200 напрямую нельзя.

**Пересобрать входы:**

```bash
python3 scripts/build_etalon_input.py
```

Из обоих файлов берётся **только сырой текст покупателя**. Перевод, название
детали и ответ боевой системы кладутся в поля с префиксом `reference_` и на
вход конвейера не подаются — иначе мерился бы не конвейер.

## 5. Цепочка: какой модуль за что отвечает

Запрошенный маршрут `retriever → shortlist → arbiter → confidence → ASK_BUYER`
целиком:

```
сырой текст покупателя
  │
  ├─ avtozap/segmenter.py     Layer 0, LLM PASS A по промпту проекта (заморожен)
  │  └─ avtozap/layer0.py     детерминированный запасной сегментатор
  │                           → список атомарных предметов (item_raw)
  │
  ├─ avtozap/oem.py           извлечение каталожных номеров, MATCH / CONFLICT
  ├─ avtozap/photo.py         слой фото-доказательств
  │
  ├─ avtozap/retriever.py     АДАПТЕР над кодом проекта. Сам поиск не переписан:
  │  │                        vendor/retriever_v2/ — код проекта как есть,
  │  │                        правились только пути к файлам.
  │  ├─ avtozap/lubricants.py вязкость 5w-40 / 0/20 → подсказка «моторное масло»
  │  ├─ avtozap/head_ranking.py надбавка 0.01 кандидату, чьё ИМЯ содержит
  │  │                        головное слово запроса (последнее слово, известное
  │  │                        словарю)
  │  └─                       → SHORTLIST, лимит 24, отсортирован (-score, код)
  │
  ├─ avtozap/arbiter.py       ARBITER V3. Промпт ЗАМОРОЖЕН и защищён sha256.
  │                           Возвращает decision + external_code +
  │                           confidence ∈ {high, medium, low}
  │
  ├─ avtozap/validator.py     правила V1–V7 поверх ответа арбитра
  ├─ avtozap/ambiguity.py     правила листа AMBIGUOUS_RULES словаря v7
  │
  └─ avtozap/policy.py        CONFIDENCE → ДЕЙСТВИЕ
     avtozap/pipeline.py      сборка всего перечисленного
```

### Порог уверенности

`ACCEPTED_CONFIDENCE = {"high", "medium"}` в `avtozap/config.py`. Ответ с
`confidence: low` до покупателя как код не доходит: правило **V7** валидатора
понижает его, и цепочка уходит в переспрос.

Порог поставлен предварительно. Окончательно его выбирают **по таблице, которую
печатает живой прогон** — доля попаданий отдельно для high, medium и low. Пока
прогона нет, порог — гипотеза.

### Правила валидатора V1–V7

| | действие | когда |
|---|---|---|
| V1 | REJECT | выбранного кода нет в словаре |
| V2 | REJECT | выбранный код отсутствует среди кандидатов shortlist |
| V3 | DOWNGRADE | запрошенного объекта нет — выбран родитель или сосед |
| V4 | DOWNGRADE | конфликт с OEM-номером не разрешён безопасно |
| V5 | REJECT | Layer 0 оставил в предмете несколько разных типов деталей |
| V6 | REJECT | состояние конвейера внутренне противоречиво |
| V7 | DOWNGRADE | уверенность `low` |

V2 — ключевое для понимания потолка: код вне shortlist отвергается, даже если
модель его назвала. Поэтому потолок ретривера и есть жёсткая граница.

### Действия (правило заказчика, `avtozap/policy.py`)

| действие | когда |
|---|---|
| `ANSWER` | деталь определена |
| `ASK_BUYER` | не уверены — просим описать другими словами |
| `ASK_PHOTO` | покупатель сам пишет, что не знает названия |
| `PASS_TO_SHOP` | второй заход (`--attempt 2`) не помог — сырой текст магазинам |
| `ERROR` | сбой конвейера |

Просьба о фото приоритетнее «отдать магазинам». Правило заказчиком заморожено —
логика `decide_action` не менялась ни разу.

### Слой неоднозначности (новое в v7)

`avtozap/ambiguity.py` исполняет лист `AMBIGUOUS_RULES`. Правила извлекаются из
самого словаря скриптом `scripts/extract_ambiguous_rules.py` в
`data/ambiguous_rules.json`; тест сверяет файл с листом до буквы, руками там
ничего не переписано.

Слой понадобился потому, что снятия алиасов оказалось недостаточно: на голом
`park radari` движок всё равно отдаёт `EL-013` со score 1.0, на `teker sensoru`
срабатывает контекстное правило `context:teker+sensor`. Это закреплено тестом
`test_the_engine_alone_would_still_answer_confidently` — если словарь однажды
научится молчать сам, тест упадёт и слой можно упростить.

**Голым** термин считается, если в запросе кроме него нет ничего, кроме слов
положения и вежливости (`arxa`, `sol`, `lazımdır`). Дописал значащее слово —
слой молчит, и отвечает словарь: `porog sveleri` → KZ-030, `park radari bloku`
→ EL-014.

Действие остаётся `ASK_BUYER` — правило заказчика не менялось. Меняется только
текст вопроса: вместо общего «опишите другими словами» задаётся вопрос из
словаря, на который отвечают одним словом.

## 5a. Словарь: поставка плюс одна согласованная правка

Словарь в пакете — это поставка v8 **с одной согласованной правкой**, и об этом
надо знать при сверке.

Убрана форма `aktivatur turbnun ustunde olan` у MU-038: это не термин, а целое
предложение, и вместе с ним в индекс попадали служебные слова `üstündə` и
`olan`. Из-за них KZ-083 «Лючок топливного бака» проседал с 0.9999 до 0.88,
хотя сам в словаре не менялся вовсе. Замена — контекстное правило
`aktivatur + turb` → MU-038.

| где что лежит | |
|---|---|
| `scripts/apply_agreed_dictionary_edits.py` | сама правка; `--check` говорит, применена ли |
| `data/reference/AVTOZAP_slovar_v8_FINAL_original.xlsx` | оригинал поставки, для сверки |
| `data/context_rules_local.json` | правило-замена, как данные |

**Вендорный код не тронут.** Правило подаётся в `CONTEXT_RULES` — структуру
данных проекта — до того, как `AmbiguityLayer` строит из неё индекс
(`avtozap/dictionary.py::_apply_local_context_rules`). Поэтому его видят и
ретривер, и движок `match()`, а файл проекта остаётся байт в байт.

Проверено: контрольный прогон после правки **не изменился ни на одну строку**
(500 / 68 / 136), rank#1 на обоих эталонах вырос с 539 до 540.

## 6. Дубли кодов — `data/duplicate_codes.json`

Механизм: код-дубль заменяется каноническим **на входе** (при сборке эталона) и
**на выходе** (перед выдачей наружу). Предлагать арбитру исчезающий код нельзя,
и две карточки одной детали в shortlist только сбивают выбор.

Текущее содержимое — три пары, все подтверждены заказчиком:

| дубль | канонический | статус в словаре v7 |
|---|---|---|
| RG-04 | MU-089 | деактивирован в v7 (`is_active = No`) |
| SO-025 | SO-005 | деактивирован в v7 (`is_active = No`) |
| MU-012 | MU-078 | **остался активным** |

Проверено: деактивированные коды в кандидаты не попадают ни на одном из
контрольных запросов.

## 7. Полный список команд воспроизведения

```bash
# 1. Все проверки (385 тестов, сеть не нужна, ~20 секунд)
python3 -m pytest -q

# 2. Пересобрать входы эталонов из размеченных файлов
python3 scripts/build_etalon_input.py

# 3. Потолок и rank#1 на обоих наборах (API не нужен)
python3 scripts/score_etalon.py
python3 scripts/score_etalon.py --etalon data/etalon_200.jsonl

# 4. Пересобрать правила неоднозначности из словаря
python3 scripts/extract_ambiguous_rules.py

# 4a. Применить согласованные правки словаря (--check только проверяет)
python3 scripts/apply_agreed_dictionary_edits.py --check

# 5. Живой прогон — ЕДИНСТВЕННОЕ, что требует ключа OpenAI
python3 PROGON_ETALON_469.py      # точность
python3 PROGON_ETALON_200.py      # поведение и таблица confidence
```

Зависимости: `pip install openai rapidfuzz openpyxl`. Ключ читается из
`OPENAI_API_KEY`, при отсутствии запрашивается скрытым вводом и **никуда не
сохраняется** — ни в один файл результатов он не попадает.

## 8. Чего в этих цифрах НЕТ

Честно и явно, чтобы не искали:

1. **Точности живого прогона.** Ключа API в среде разработки нет, поэтому
   цифры, которую надо ставить рядом с боевыми 128, не существует. Подставлять
   вместо неё результат mock-арбитра нельзя: заглушка осторожна по построению и
   описывает саму себя, а не цепочку.
2. **Оценки арбитра.** Всё измеренное — до арбитра. Разрыв между потолком
   (467/469) и живым результатом и будет ценой его ошибок.
3. **Проверки OEM-веток.** `MATCH` и `CONFLICT` не на чем проверить: файла
   `data/oem_catalog.json` нет вовсе, каталога соответствий «номер → деталь»
   пока не передавали. Номера из текста извлекаются и сейчас, но сравнить их
   не с чем.
4. **Сравнения с числом 432/469 из вашего changelog.** Оно и наши 467 — разные
   величины: 432 это точность матчера, 467 — потолок shortlist. Ставить их
   рядом нельзя.
