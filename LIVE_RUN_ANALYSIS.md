# Разбор живого прогона 300 заявок (31.08.2026)

Материалы: `AVTOZAP_END_TO_END_FRESH_300.csv` (503 строки) и одноимённый `.log`.
Итог прогона: `select=348, unknown=137, clarify=18, errors=3`.

## Чей это прогон

**Не этого харнесса.** В CSV 15 колонок против 43 моих, общих имён только два
(`rfq_id`, `original_text`); формат лога (`CASE … ERROR`, `DONE inputs=…`) тоже
другой, а ошибки разбора JSON в нём русскоязычные («Недопустимый переданный
объект, ожидается ":" или "}"»), каких не выдаёт модуль `json` в Python.
Похоже на Windows-прототип. Это важно: часть выводов ниже касается того
runner'а, а часть — общая.

---

## 1. Кодировка — диагноз верный, прогон непригоден

Подтверждаю: `latin-1`-декодирование воспроизводит порчу **байт в байт**.

```
пришло : 'Matorun paduÅ\x9fkasÄ±'
было   : 'Matorun paduşkası'
```

Порча только на обратном пути: `original_text` (из входного файла) **чистый**,
а `layer0_item_raw` (из ответа модели) битый — 249 строк из 503.

**Цена ошибки измерена:**

| строки | select |
|---|---|
| чистые (254) | 75.6% |
| битые (249) | 62.7% |

Разница 13 п.п. Прогон как измерение качества не годится — согласен полностью.

**Но у Python-харнесса этой болезни нет.** Проверено: `httpx` (транспорт SDK
`openai`) кодирует тело запроса явно в UTF-8 и декодирует ответ по заголовку
`charset`. Тест `test_the_python_transport_round_trips_azerbaijani` это
фиксирует. Чинить нужно тот runner — либо перейти на этот.

**Что добавлено здесь:** `avtozap/encoding_guard.py` ловит mojibake в тексте,
пришедшем от модели. На реальных данных: **249 из 249 пойманы и восстановлены,
0 ложных срабатываний** на 503 чистых `original_text`. Если порча появится,
`summary.md` начинается с «⛔ ПРОГОН НЕПРИГОДЕН ДЛЯ ОЦЕНКИ КАЧЕСТВА» — молча
испортить 300 заявок больше нельзя.

---

## 2. Обрыв длинных ответов — верно, и это касалось моего кода

Три заявки на десяток деталей оборвались на полуслове. У меня стоял общий
лимит `max_tokens=700` — для такого JSON мало.

Исправлено: у сегментера лимит 4000, у арбитра 500, и появился отдельный класс
ошибки `TruncatedResponse`. Обрыв определяется по `finish_reason == "length"` и
**не повторяется** — при тех же параметрах он повторится один в один. В том
прогоне это выглядело как «ошибка разбора JSON» и уводило расследование не туда.

## 3. Layer 0 — здесь я не согласен

Вывод «Layer 0 не дорезает» данными **не подтверждается**.

Из 12 отказов «в запросе две разные детали» **11 пришлись на предметы, которые
Layer 0 уже разрезал правильно**:

| `original_text` | предметов Layer 0 | этот `item_raw` | отказ арбитра |
|---|---|---|---|
| `Naklatka və tormuz disk` | 2 | `tormuz disk` | «two different parts: Naklatka and tormuz disk» |
| `Ön və arxa bufer sel plusa lazımdı` | 2 | `arxa bufer` | «both front and rear bumpers, two different parts» |
| `Turbo katrici və turbo zbor` | 2 | `turbo zbor` | «two distinct parts: turbo katrici and turbo zbor» |
| `Matorun paduşkası matorun sepi remeni` | 2 | `Matorun paduşkası` | «engine mount and timing chain» |

`item_raw` здесь — одна деталь. Арбитр судит по `original_text`.

Причина видна в самом промпте V3: правило звучит как «If **item_raw itself**
clearly contains TWO DIFFERENT requested part types», и про `original_text` в
промпте **не сказано ни слова** — это поле добавляет харнесс, и оно перетягивает
внимание.

Промпт заморожен, поэтому исправлено на стороне харнесса, без правки промпта:

* `item_raw` идёт **первым** полем payload, `original_text` — после;
* добавлено поле `other_items_in_same_message` — остальные предметы сообщения
  как **факт**, что ими занимаются свои запуски. Это данные, не указания.

Практический вывод: **дополнительная работа над Layer 0 эти 11 случаев не
исправит** — они уже разрезаны. Реально «не дорезан» только один случай:
`Qabag fara amaziator` (фара + амортизатор в одной строке без разделителя).

Оговорка: подтвердить, что перестановка payload снимает ложные отказы, можно
только живым прогоном. Логика причины прочная, но это гипотеза, а не замер.

**Про «признак должен оставаться при своей детали» — согласен полностью**, и это
уже так. `ön bufer arxa bufer` остаётся одним предметом; дорезка срабатывает,
только если куски указывают на **разные группы словаря**. Тесты
`test_one_part_in_several_positions_is_never_split` и
`test_positions_stay_attached_to_their_part` это держат.

Дополнительно: предмет с двумя разными деталями теперь дорезается **до**
арбитра. Раньше он отвечал `clarify`, и обе детали терялись; теперь каждая
получает свой запуск.

## 4. Словарь — 7 из 10 слов уже находятся

Ни одно из десяти слов не является точным термином словаря, но ретривер и так
доводит до правильной детали:

| слово | топ-кандидат ретривера | нужно ли в словарь |
|---|---|---|
| `pavarotnik` | KZ-008 Поворотник | нет, находится |
| `podkrelnik` | KZ-029 Подкрылок | нет |
| `MAP sensor` | MU-045 MAP-датчик | нет |
| `EVAP` | YA-007 Система EVAP | нет |
| `apornu` | EY-002 Тормозной диск | нет |
| `natlatka` | EY-001 Тормозная колодка | нет |
| `Tiyaqa ucluqu` | SU-001 Наконечник рулевой тяги | нет |
| `abornu` | RG-04 Воздушный патрубок ❌ | **да** |
| `Abirsofka` | KZ-002 Кронштейн бампера ❌ | **да** (нужен KZ-003) |
| `Avtopadsos` | AS-002 Опора амортизатора ❌ | **да** |

Проверено на строках самого прогона: там, где арбитр написал «No candidate
matches 'natlatka'», деталь EY-001 стояла в shortlist **первой**. То же для
`Map sensor` (MU-045 первый) и `Sol qabaq pavarotnik` (KZ-008 третий).

То есть по семи словам узкое место — **не словарь и не поиск, а решение
арбитра**. Добавление их в словарь эти случаи не сдвинет. Стоит добавлять
`abornu`, `Abirsofka`, `Avtopadsos` — остальные семь силы не потратят зря.

Оговорка: shortlist того прогона в CSV не сохранён (есть только
`candidate_count`), так что «кандидат был на месте» — это про мой ретривер.
Чтобы такие споры закрывались данными, в моём CSV shortlist пишется целиком
(`retriever_candidate_codes`, `retriever_scores`, `retriever_reasons`).
